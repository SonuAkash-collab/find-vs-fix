# HANDOFF: LoRA runs (for Sidhant, Piyush, Siddhant)

**Nothing here has been run yet.** This is the plan for the next step: repeat our pilot, Phase 2 and Phase 3 with
**LoRA** instead of full fine-tuning, on GPT-2 first, then Pythia-160M. Read PROJECT_SPEC.md (the spec and the rules), then
RESULTS.md and NIGHT2_REPORT.md (what full fine-tuning gave us).

**LoRA in one line:** instead of changing a big weight matrix W, train two small matrices A and B (rank r) and use
W + (alpha/r)·B·A. Low rank (4) = very few new weights; high rank (64) = many more.

## The hard rule (same as the rest of the project)
**No number goes into any report, slide or RESULTS.md unless it comes from a logged run in this folder.** That means a saved
config, saved per-seed output (results/*.json), and it can be re-run with one command. Never type a number by hand. RESULTS.md
is generated by `src/report.py` only.

## 2. LoRA settings (GPT-2)
- Library: `peft`. `LoraConfig(r=..., lora_alpha=..., lora_dropout=..., target_modules=[...], fan_in_fan_out=True,
  bias="none")`.
- **Targets: `attn.c_attn`, `attn.c_proj`, `mlp.c_fc`, `mlp.c_proj`** in every block. Both attention and MLP get
  adapters, so the attention-vs-MLP split from Phase 2b can be compared directly. Note: `c_proj` alone would match
  both attention and MLP, so write the full suffixes.
- GPT-2 uses `Conv1D` layers (weights stored transposed), so **`fan_in_fan_out=True` is required**. Without it the
  adapters get the wrong shape or silently do the wrong thing.
- The classifier is still the frozen tied `lm_head` restricted to " positive"/" negative". Nothing new is trained on top.
- **Ranks: 4 (low) and 64 (high).**

## 3. Merge before saving (important)
After training, call `model = model.merge_and_unload()` and save that with `save_pretrained(runs/<name>/model)`.
The merged model is a plain GPT-2 with the same weight names, so `checks.py`, `logit_lens.py`, `swap.py` and
`retrain.py` work on it unchanged. Assert after merging that the state-dict keys equal those of a normal GPT-2
(no `lora_` keys left). Also save the unmerged adapter separately (small) in case we need it later.

## 4. Choosing alpha and lr: a small pilot on seed 0 only
LoRA usually needs a higher lr than full fine-tuning, so our 5e-5 may not work. Before the pilot,
**write the selection rule into PROJECT_SPEC.md and commit it** (pre-registration, as we did for Phase 2b/3). Suggested rule:
- **Pilot grid (fixed, 12 runs, seed 0 only):** alpha = 2r fixed (r=4 → alpha 8, r=64 → alpha 128),
  lr ∈ {1e-4, 3e-4, 1e-3}, rank ∈ {4, 64}, {shortcut, clean twin}. That is 3 lr × 2 ranks × 2 data = 12 runs.
  Alpha is **not** tuned: it stays 2r.
- Pick the **smallest lr** at which **both ranks pass all the existing checks** (task ≥ 0.80 on "none"; shortcut gap ≥ 0.20;
  clean twin |gap| ≤ 0.05), using the same lr for both ranks. A setting counts only if the shortcut run and its clean twin
  both pass, for that rank and lr.
- Save every pilot run's metrics in `results/lora_pilot/` and record the choice and the reason in `configs/lora.yaml`.
  Each of the 12 runs logs its GPU, torch and transformers versions (§0, step 6).
- If no setting passes for both ranks: **stop and tell Sonu.** Don't widen the grid on your own.
The 10% prevalence fallback from PROJECT_SPEC.md still applies only to "shortcut learned" failing, and must be recorded.

## 5. Matched clean twins
Every shortcut LoRA run gets a **clean LoRA twin with the same rank, alpha, lr and seed**, trained on

## 6. What to expect from Phase 2b's embedding result
LoRA does **not** train the embeddings (wte, wpe) or ln_f. Phase 2b found the embeddings play **no part** in the
shortcut: swapping the name-token rows did nothing, and all 12 blocks alone recreate the shortcut with clean embeddings
(NIGHT2_REPORT.md, rule 2b-b). So **LoRA should still be able to learn the shortcut**. If it doesn't, that's a result,
not a bug to tune away. One more expectation: LoRA changes every block a little, so the swap map may look more spread
out than with full fine-tuning.

## 8. Pythia-160M: what changes
Pythia is a different architecture, so the GPT-2-specific names in the code need a small **model adapter**
(one place that gives block prefix, final norm, output matrix and tokenizer).
- Blocks: `gpt_neox.layers.<b>.` (12 blocks). Final norm: `gpt_neox.final_layer_norm`. Output: **`embed_out`, which
  is NOT tied** to the input embedding `gpt_neox.embed_in`. So "swap only the name rows" needs no tied-weights special case,
  but the output matrix must still stay from the edited model.
- Per-block tensors: `input_layernorm`, `attention.query_key_value`, `attention.dense`, `post_attention_layernorm`,
  `mlp.dense_h_to_4h`, `mlp.dense_4h_to_h` (weight + bias each = 12). Check the actual state dict: some transformers
  versions also store buffers (e.g. rotary `inv_freq`, attention masks). Fix the "12 per block" / "6 per half" asserts
  to the real count. Don't delete the asserts.
- Attention half = `input_layernorm.*` + `attention.*`; MLP half = `post_attention_layernorm.*` + `mlp.*`.
  Pythia runs attention and MLP **in parallel** (both read the same input), not one after the other as in GPT-2. Mention
  this when comparing halves.
- LoRA targets for Pythia: `attention.query_key_value`, `attention.dense`, `mlp.dense_h_to_4h`, `mlp.dense_4h_to_h`.
  These are normal `Linear` layers, so **`fan_in_fan_out=False`** here.
- Logit lens: apply `gpt_neox.final_layer_norm`, then `embed_out` (same "don't apply the final norm twice at the last
  layer" rule).
- **Checks before any Pythia training** (save the output to `results/pythia_tokenizer_check.json`):
  1. `" positive"` and `" negative"` are each **one token** in Pythia's tokenizer. If not, stop and tell Sonu
     (changing label words is a design change).
  2. The three names (Tavin Morrell, Dorvan Hastrow, Corwin Halvey) have **equal token counts** in Pythia's tokenizer.
     If not, stop and tell Sonu. New names would mean new data, which is his call.
  3. Every test prompt fits in max_len 160 in Pythia tokens. Reviews were cut at ~100 *GPT-2* tokens.
  4. Base Pythia has no name preference (the same base check as `checks.py --base`).

## 8b. Pythia-160M: full fine-tuning settings (pre-register before the first Pythia run)
- **Model id:** `EleutherAI/pythia-160m` (the final checkpoint; no `revision`). Record the exact id in the config.
- **Padding:** Pythia's tokenizer has no pad token. Set pad = eos and right padding, exactly as `get_tokenizer()` does for
  GPT-2, and find the last real token from the attention mask. Assert that the score is read at the last *real* token.
- **Everything else as the GPT-2 pilot:** full fine-tuning, nothing frozen, fp32, AdamW, weight decay 0.01, 6% warmup +
  linear decay, batch 16, 3 epochs, max_len 160, the same data files and the same loss over " positive"/" negative".
- **Learning-rate rule:**
  1. Start with **lr 5e-5** (the same as GPT-2), seed 0, shortcut + clean twin.
  2. If both pass all the checks (task ≥ 0.80 on "none"; shortcut gap ≥ 0.20; clean |gap| ≤ 0.05), use 5e-5 for everything.
  3. If either fails, try **2e-5 and 1e-4** (seed 0, shortcut + clean) and pick the one closest to 5e-5 at which both pass.
     If both pass, take 2e-5. Record every attempt in `results/pythia_pilot/` and the choice in `configs/pythia.yaml`.
  4. If none passes: **stop and tell Sonu.** The 10% prevalence fallback is still the only allowed data change, and only
     for "shortcut learned" failing, with Sonu's OK.
- **Memory:** about the same size as GPT-2 (around 160M parameters), so full fine-tuning in fp32 should fit like the GPT-2
  pilot did (about 3.6 GiB peak). Measure it on the smoke test before the real runs anyway.
- **Runs:** {shortcut, clean} × seeds {0, 1, 2} = 6 runs, named `py160_shortcut_seed<s>` / `py160_clean_seed<s>`, results under
  `results/pythia160m/`. Then checks → logit lens → Phase 2 + 2b swaps → Phase 3 retraining, the same rules as GPT-2.
- **Then Pythia LoRA:** use the rank, alpha and lr picked in the GPT-2 LoRA pilot (§4). If they fail the checks on Pythia, run
  the same 12-run pilot grid on Pythia (pre-registered first), don't hand-tune.
- **Reporting rule (TA point 4):** for every GPT-2 finding, say only **"reproduces" or "doesn't reproduce" on Pythia-160M**.
  Never explain a difference by architecture.
